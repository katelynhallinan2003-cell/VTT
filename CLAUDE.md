# Working rules for this project

These are standing orders from the user (set 2026-11-22). Follow them without being asked.

## Read this file first, every run

Read `CLAUDE.md` (this file) and `WIP.md` before doing anything else in a session. When a change sets a new design precedent
(where data lives, who may write it, how a feature is meant to behave), add it to *Design precedents* below in the same commit.

## Ship straight to `main`

- When a piece of work is finished, **commit it and push it directly to `main` on `origin`.** No feature branches,
  no pull requests, no asking for permission first.
- Check before pushing: `npx tsc --noEmit` and the tests for the changed feature must pass. Do not push broken work.
- One issue, one commit where practical, with `WIP.md` updated in the same commit.
- **More than one session may be working on this repository at the same time.** Run `git fetch` before you start and before you push. If `main` has moved, rebase your work onto it (`git rebase origin/main`), run the checks again, then push. In `WIP.md` keep both sides and renumber your own issues if the numbers collide.
- Never force-push. If a rebase has conflicts in code you cannot settle with confidence, or the push is refused for another reason (branch protection, no access), stop and tell the user.
- Still ask first for anything destructive or hard to undo that the user did not ask for (rewriting history,
  deleting branches or data, touching the live Firebase project).

## Keep `WIP.md` up to date

`WIP.md` in the repo root is the list of every issue the user has given.

- **At the start of a session, read `WIP.md`.**
- **The moment the user gives an issue** (a bug, a feature, a change, including one that arrives while you are
  mid-task), add it to *Open* in `WIP.md` with the next number and today's date, then carry on. One entry per issue:
  if a message contains three issues, add three entries.
- Mark the one you are working on `(in progress)`.
- **When an issue is finished** (built, tested and pushed), move its entry to the bottom of the *Completed* list,
  tick it `[x]`, and add the completion date and a line on what shipped. Never delete entries.
- If the user says something still does not work, move it back to *Open* and note what is left.
- **Before every report to the user,** re-read their recent messages and check that every issue in them is in `WIP.md`.
- A plain question that needs no change to the project is not an issue and does not go in the file.
- An issue that cannot move until the user does something is marked `(waiting on user)`; remind them of these when it is relevant.
- The *Ideas* section holds suggestions nobody asked for. Do not build them unless the user asks. You may add your
  own ideas there, never to *Open*.

## Project habits

- Stack: Vite + TypeScript + Preact + PixiJS 8, Firebase Realtime Database (rules generated by `npm run rules`), static hosting on GitHub Pages.
- Run it: `npm run dev`, then open `http://localhost:5173/?demo` (demo mode, no Firebase needed).
- Run the checks for the change. `npm test` selects unit tests affected by uncommitted changes. For UI changes, choose the relevant feature group (`npm run test:maps`, `test:terrain`, `test:vision`, `test:drawing`, `test:tokens` or `test:table`) or a specific browser scenario. Use `npm run test:all` for a deliberate full check.
- Browser tests: `npm run build`, `npx vite preview --port 4174 --strictPort --host 127.0.0.1`, then `node tests/e2e/<name>.mjs`. They need Chrome (`CHROME_PATH` to say where) and write screenshots to `/tmp/shots` (`C:\tmp\shots` on Windows).
- Changing the printed-grid finder (`src/core/gridcut.ts`, `hexcut.ts`, `mapgrid.ts`): add a map to the corpus that shows the problem first, then fix it. Never tune it against one picture.
- Tell the user about database rule changes: `database.rules.json` has to be republished in the Firebase console by hand.
- End commit messages with the attribution lines required by the session.

## Design precedents

- Store recoverable image originals once per hosted URL in a bounded local store. Only the GM publishes verified replacements. Preserve scene geometry and edit only references that still name the missing image.

- **Sight across elevation.** Use the viewer's unrounded standing or flying altitude plus 5 ft per token size unit. A finite drawn wall at eye level can be seen over. Each scene saves **Elevation gradients block vision** under advanced fog settings, default off. Drawn walls and abrupt terrain boundaries cast shadows in both modes. By default a continuous painted slope can receive a shadow. Enabling the switch also lets intervening crests cast shadows. Looking downhill, lower ground returns to view where it clears the sightline past a rim. Use finished terrain contours, preserve brushed deck openings and ignore numerical seams between touching regions. Allow half a foot of detail downhill and some relief on the near face uphill. Sample continuous slopes in map coordinates and evaluate a sloping rim at the actual crossing. Feather the artwork separately from token visibility. Compose terrain sight into the bounded fog bitmap so zooming never allocates a GPU mask for the entire zoomed map. Current sight, lights and exploration use the same scene setting. Movement continues to use the underlying terrain.

- **Sight runs off the main thread and draws on the GPU.** Token sight, lights and darkvision are solved in `board/sight.worker.ts` (scene geometry rebuilt there from the ground drawings and stored walls, `core/sightScene.ts`), traced only over the screen plus a margin, newest request wins. The board never waits for it: the last answer stays up. `FogView` cuts the sight out of the bounded fog canvas in one shader; `LightLayer` draws the night wash, glow and dark-sight mask into screen-bounded render textures; panning past the drawn part redraws on the GPU without a new solve. Browser tests wait for `board.sightSettled()`. Unpainted cracks enclosed by painted ground and under half a foot wide are seams for sight, downhill steps under a foot cast no shadow (full by two feet), and detached visible slivers under a foot across are dropped. Movement still uses the exact terrain. Terrain walls are shown, counted and selected as runs (`wallChains`); the pieces stay underneath.

- **Hide everything.** Cover the scene and enable token sight together. Current sight still follows walls, lighting and darkvision. Undo restores the previous fog and sight settings. A completely clear fog mask skips token sight and exploration until fog returns. Ambient darkness and lamps still apply.

- **Elevation and movement.** Every elevation overlay uses the same translucent topographical palette, including during movement. Elevation numbers appear wherever the overlay is visible and a label fits. Select picks one connected patch at its finished height. Every painted height change is a terrain wall and charges climbing up or down. Derived boundaries follow the finished painted terrain, including additive strokes and erasers.
- **Bridge openings.** Walls Edit and Erase operate on authored walls and painted elevation boundaries. Store only the edited spans with the scene walls. Erasing a span opens sight through it and preserves the painted deck height. A route can pass beneath a deck through two openings. Ending or placing a deliberate stop on the deck counts the climb.
- **Drawn walls and flight.** Height zero blocks movement. A finite wall can be climbed, including both faces on level ground. Closed doors and windows keep their existing movement rules. Flight counts the vertical travel required to clear the terrain and finite walls along the measured route.
- **Test moves.** Count terrace heights on the ground traversed between crossings. Touching a terrace at a turn adds no climb. On square grids, give the cursor room to cross a corner diagonally. Preserve turns within a drag and send them with shared previews. Only deliberate multi-step stops receive individual distance labels.

- **Gradient editing.** Connect neighboring automatic boundary runs at the same height along the ring, preserving individual edits. Fill unpainted holes respects painted islands, including 0 ft terrain. Fill all holes can absorb enclosed islands into a gradient. An opening connected to the exterior stays open.

- **Terrain brushes.** In Paint, choosing Added on top starts a fresh stroke above existing ground. Each gesture adds its height once where it passes. In Select, Set Height assigns an absolute elevation to the selected ground. Gridless scenes use round brushes sized in calibrated feet for height, difficult ground and erasing.

- **Printed square grids.** Learn the ink's RGB shift from repeated strokes and nearby terrain. On dotted JPEGs, account for the recurring light and dark fringes around the dots. Check the rendered result at native-pixel zoom on both smooth ground and painted edges.

- **Map scans and display resolution.** Detect printed grids on a bounded sample of the original picture. A device can shrink the displayed texture independently. Store the detected spacing in original picture pixels. Save the repaired PNG in the browser per source, removal settings and display limit. Open it directly when the scene asks to hide the grid.

- **Library picture deletion.** One click removes the entry. In the same write, move any private ImgBB deletion link to the owning DM's cleanup list under My library. Hosted deletion is optional. Campaign exports and shared scenes and tokens carry only picture URLs.

- **Maps without a clear printed grid.** Start gridless with free movement and straight-line measurement. The DM can calibrate ten feet with two points, then choose squares, hex rows, hex columns or no overlay. Changing the overlay preserves the map scale. Grid type and calibration belong to the scene. Switching scenes reads its saved choice, and manual calibration takes precedence over a pending automatic scan.

- **Where data lives.** Anything the DM alone may see or write goes under `tables/$tid/dm/` (owner-only, free-form: scene index, scene folders, character hit-point memory). Public scene data is under `scenes/$sid`. Things tied to the DM's Google account (image library, saved token templates) are under `users/$uid` and only the allow-listed DM can write there.
- **Players have no account.** They are anonymous per browser, so nothing a player wants to keep may be tied to their browser's uid. A player's saved characters live in the table (`tables/$tid/chars/$rid`), and a player's `rid` (identity) says which library is theirs. A returning player picks their name on the join screen to take their `rid` back; the DM's screen then gives the old entry's tokens to the new uid and removes the old entry once it is offline.
- **Hit points are the DM's.** Players only see what the token's health display allows; the DM's screen files each saved character's hit points (`dm/chars/$cid`) and restores them when the character arrives in another scene.
- **Rules.** `database.rules.json` is generated by `npm run rules` from `scripts/build-rules.mjs` and tested in `tests/rules.test.ts`. The allowed DM emails are data under `config/allowedEmails`, not part of the rules file, so republishing rules never removes them. Every rules change must be listed in the report to the user as "republish `database.rules.json`" (and tell them to wait for the final file if more rule changes are coming).
- **A picture dropped on the page.** On a table with no scenes it is the map of a first scene (it opens New scene, it never creates anything by itself); once there are scenes it is a new token. A window that takes drops (New scene) takes them anywhere on the page while it is open. The page always says what a drop will do while something is dragged over it.
- **Map framing.** Fit the view when the main map is added or replaced. Returning to the same picture in the same scene restores that viewer's pan and zoom.
- **Printed-grid finder.** Both finders (squares in `gridcut.ts`, hexes in `hexcut.ts`) mark their answer 0 to 10 on the same scale; `AUTO_GRID_STRENGTH` in `mapgrid.ts` is the one place that decides what is set up without asking. They look at the picture only: the scene's grid size is never trusted on a fresh map. Evidence has to be thin lines (darker or lighter than BOTH sides), seen in many parts of the picture. The drawn maps in `tests/helpers/gridcorpus.ts` are the measure: a new failure becomes a new map there before it is fixed.
- **Basics first, the rest deeper.** Anything a new DM needs in the first ten minutes is one click away and comes first in its window (the picture before the paint tools, who owns a token before its flying height). Rarer things go lower, behind a tab, a folded section or a "…tools" button: Settings is four tabs (Table, Pictures and files, You, Mouse and keys), the toolbar is everyday tools and then the DM's scene tools, options that depend on a switch only show once the switch is on.
- **Words.** A hint under a control is one short sentence that says what the user needs to decide, not how the feature works inside; longer explanations go in the tooltip or the README. The same thing has the same name everywhere: "picture" (not "image"), "Players can see it", "Only on your screen", "Hide everything". When a label that the browser tests look for is reworded, keep the phrase they look for or change the test in the same commit.
- **Nothing covers anything else.** What hangs from the top of the screen (notes, the test-move bar, warnings, the turn order) is one stack: it sits between the two halves of the top bar when it fits there and in a row under the top bar when it does not (`TableView` measures this; see the end of `styles.css`). The bar for the selected token keeps clear of the side panel. Check new things at 1366 by 768 as well as on a big screen.
- **Windows and right-clicks.** On Windows the browser's "context menu" event arrives after the mouse button is let go, on Linux and Mac when it is pressed. Never open or close anything of ours in answer to that event: only stop the browser's own menu with it. (The browser tests run on whatever machine you are on, so run them on Windows too.)
- **Old tests drift.** When a label or flow changes, update the e2e batches that used it; run the full e2e regression against a frozen build before pushing a round.

- **Lights are props, not tokens.** A torch or other light-only mark (`isLightMark`: no shape, no picture, has a light) is not in the DM's Tokens list (it has a folded "Lights" list under it), not in the initiative order, and cannot be claimed or given to a player. A creature carrying a light is an ordinary token. A light has its own short editor, tag and menu: only its light, its name, "Hide the marker from players" and locking. No picture, ring, size, shape, sight, darkvision, initiative, auras, effects, library, **hit points, height or flying, name label**: when adding a field to the token editor, decide whether a light needs it and keep it out of the `lightOnly` branch if not. **A light's `hidden` hides only its marker, never its light.** A light-only mark is always stored in the public tokens (`scenes/$sid/tokens`, never under `dm/`) so players receive its light; `hidden` on it is the wire field `hide: true` (`tokenToWire`, `normalizeToken`, and `tokenPath` in the client decide where a token lives, and a token that stops or starts being a light moves with it). The board gives players no view (no marker, nothing to click) for a hidden light but still counts its light (`lighting()`); a creature carrying a light that is hidden is still gone with its light. New lights (Place a light, Auto-add lights) start hidden. A hidden light found in the DM-only part (older tables) is moved to the public part by the DM's screen when the scene loads (`queueLightMove`). No rules change: token fields are not validated.

- **Drafting from the map picture.** "Detect walls" and "Auto height map" read the main map picture in the browser (a sample of at most 1400 or 1100 pixels a side; nothing is uploaded) and only ever *propose*: the DM sees the result drawn over the picture, tunes it, and one button adds it as a single undoable step. Detected walls are plain walls 10 ft high; doors, windows and one-way cliff edges stay manual. Heights are never guessed from the picture's shading: the DM marks known heights. The pixel work lives in `core/walltrace.ts` and `core/autoHeight.ts` (plain arrays, unit-tested on drawn maps in `tests/walltrace.test.ts` and `tests/autoHeight.test.ts`); a failure on a real map becomes a new drawn map in those tests before it is fixed. Solid-area ("edges") detection works from the picture rather than fixed numbers: `suggestSensitivity` sets how close the colour must be from the peak in the colour distances, the outline is traced directly (`traceContours`, then `closeMask`/`smoothPath`) and simplified to a fraction of a grid square, and a colour that is not one flat colour (`clear: false`) is drawn coarser and flagged in the window with a plain warning, never silently dumped as hundreds of scraps. Real maps are not committed (they are someone's artwork): the test builds a drawn picture with the same traits instead.

- **Grid colour.** White is the default. Colour code treats black (`0`) as a colour, never as "missing". A saved pure black (`#000`, `#000000`) is the old default from before 2026-11-23, which was always drawn white, so it still shows white; black picked on purpose is saved as `#010101` (`gridColorToSave` in `core/model.ts`).
- **Elevation and difficult terrain.** Paint, Erase and Select shape elevation areas. Make Gradient edits the selected area with absolute point or polyline heights, saved on its first paint stroke. Two or more controls define a continuous surface by inverse distance. Edge handles slide around the perimeter, including past the halfway mark. Seed shared lines from adjacent flat heights once at conversion when the difference is less than 15 ft. Overpaint clips the visible gradient perimeter used by selection and edge controls. Its saved heights and control paths stay intact underneath. New paint creates a wall where the heights differ. Select opens gradient handles directly, and Done deselects terrain. Only show hole-filling actions when applicable. Only discontinuities at the edge cost climbing. Standing height on a hex uses its centre and six interior samples. Flat and sloped terrain share a continuous tint at matching heights. Both terrain overlays appear while moving or measuring, in the terrain tool, or with the local Always show terrain setting. The DM can also keep both overlays visible to players per scene under Advanced. Gridless difficult ground follows the freehand paint. Clip elevation and difficult-ground brush footprints to the union of the map pages.
- **Dropdowns hug their text.** A `<select>` is as wide as the choice it shows (`field-sizing: content`), not as wide as its panel.
- **Tables.** The start page lists a DM's tables with Rename and Delete. Deleting clears the table entry by entry (the rules have no write at `players`, `chars` or `scenes`, only below them) and then its `owner` marker, which only the owner may remove. If the rules are not yet republished the contents are still cleared and the DM is told. Never delete anything on ImgBB along with a table.
- **Pictures come in by upload or drag, never by pasted link.** There is no "paste a link" box anywhere. A picture dragged from another web page still arrives as a link and the window shows where it is from.
- **ImgBB deletion is best effort.** Removing a library picture writes the removal and the private deletion link (the cleanup list) in one step, then asks ImgBB to delete it; the cleanup link goes only when ImgBB answers with JSON success (`deleteFromImgbb`). ImgBB documents only uploads, so never assume this works from a browser.
- **Library lists.** More than six pictures get a search box (every word must match the name). New scene shows the newest dozen, with Show all opening the rest in a wider window. Hovering shows a larger copy from `previewSource` (ImgBB's medium copy when saved; an original over 12 megapixels is never loaded for a preview).
- **First table.** Nothing offers to summon players until someone other than the DM has joined.
- **Doors and windows open; walls do not.** Both start shut (`open: false`). A shut window stops walking but never sight or spells; an open one stops nothing. A shut door stops all three. A plain wall never opens whatever its data says (`blocksMove`, `blocksSight`, `normalizeWall`). The DM opens one by clicking its handle (diamond for a door, small square for a window) or by double-clicking it in Edit mode.
- **Settings you set once are folded.** A card of switches that a DM sets once and leaves (the Walls tool's "On this map") is a `fold-head` button that is folded by default and remembers its state in that browser; anything the DM must notice (the "Turn on fog and token sight" button) stays outside the fold.
- **Auto height map.** Height marks guide connected regions along image edges. Every applied draft covers the whole map footprint, including an explicit 0 ft base for ground left over after a single marked height. The DM can turn any draft region into a gradient and match individual shared edges. This edits the surface inside its original outline. Unmatched edges keep independent heights. Two draft gradients meet at the mean of their marked region heights on a shared smooth edge. Drafts preserve existing painted ground including zero and gradients, and commit in one undo step. Scene grids do not quantize their outlines.
- **A template can be difficult ground.** The flag lives on the template (`td`); it is never copied into painted terrain. The board feeds marked templates through `templateRoughDraws` into the same difficult-ground layer the Heights brush paints, using the squares the spell can reach, and rebuilds that when drawings or walls change. Anything that asks whether ground is difficult (`isRoughAt`, `moveCost`) therefore answers for templates too.
- **Auto-add lights proposes, never places.** Like Detect walls, `core/autolight.ts` works out lamps on the picture and lights for walled rooms, the window draws them over the map, and one button adds them as one undo step (`client.addTokens`). Rooms are only the places the walls close off completely; coverage is a greedy cover with walls stopping the light, counting lights already on the map.
- **Lights ignore walls and cliffs when they are moved.** A light-only mark (`isLightMark`) is placed once and left, so `stepBlocked` never stops it; a creature carrying a light is an ordinary token and is stopped as usual. A wall still stops what the light shines on.
- **Painted light is a ground layer of its own, with a soft edge.** The DM paints it in Scene > Light and darkness > Painted light (the Light tool, `tool: 'light'`, `lightPaint: 'day' | 'dim' | 'erase'`, `lightBrush` in feet), never in the Heights panel. Strokes are `k: 'terrain'` with `dl: true` (and `dd: true` for dim light; group `dl` or `dd`) and kept apart from heights and difficult ground in `terrainOf(draws, grid, 'day' | 'dim')` (`dayOf`, `dimOf`, `isDay`). It is always a free round brush (never whole squares, so no grid seams), it never changes height or movement, and every "Clear all heights" must leave `dl` alone (it has its own "Clear painted light"). An Erase makes one eraser for each kind. It matters only when the scene is Twilight or Dark. Daylight lifts the dark fully, dim light halfway (in Dark only), and beyond the paint the light fades out over the scene's `meta.light.edge` (feet, default 20, 0 to 100; `DEFAULT_SOFT_EDGE_FT`, `MAX_SOFT_EDGE_FT`) from full strength at the paint's edge to nothing along a smoothstep, so the edge is never a step: `core/paintedlight.ts` works the fade out from an exact distance transform on a coarse grid, `paintLift` in `core/light.ts` upscales it smoothly, `paintShade` cuts it out of the wash and `paintSeen` adds it to the lit ground (ground counts as lit while at least a quarter of the light reaches it, `SIGHT_SHARE`). **Walls stop painted light like they stop a lamp:** the distance is measured round walls (a geodesic distance over a mask of wall cells, `walkDistance`, `wallCells`), so the glow beyond the paint never crosses a wall; one-way cliff edges (`one`) do not stop it. Walls are passed to `paintLift` from `LightLayer`. The gold and blue tint on the map shows only to the DM while the Light tool is on. The lighting key includes `day.sig`, `dim.sig` and the edge. Tests: `tests/paintedlight.test.ts`, `tests/daylight.test.ts`, `tests/e2e/batchZ16.mjs`.
- **Group hit points.** With two or more tokens selected the token bar has a **Group HP** button (`GroupHpPop`, `ui/groupHp.tsx`). Selecting is Shift, Ctrl or Cmd-click (in the Tokens tab or on the board) or a drag box; the popup takes one number and a mode (Damage, Heal, Temp HP), lists the tokens that have hit points with a tick (who is hit), what each will have afterwards, and a ½ chip for those that made the save (damage only; rounded down). It goes through `client.hurt` (per-token amounts, **one undo step**) or `client.giveTemp`; `applyDamage` is the one place temporary hit points soak damage first and healing is capped at the maximum. In the popup Ctrl+Z with an empty box undoes the last hit. Hit points stay the DM's: a token with no hit points is left out. Tests: `tests/grouphp.test.ts`, `tests/e2e/batchZ18.mjs`.
- **Grid settings are in one order.** Scene > Grid: grid type, Show grid, Snap tokens, Grid colour, **Fit the grid to the map** (Find and hide it, Set scale with two points, Draw a box), then three folded sections in this order: *Grid printed on the map*, *Fine tune grid* (square size, offsets, opacity), *Distance rules*. Anything the DM must notice (the alignment button) stays outside the folds.
- **An added map or empty grid can have a grid of its own** (`ExtraMap.gs` square size in px, `gv` shown or hidden, `gc` line colour, `gp` an empty grid's paper colour; `core/mapgrids.ts`). Unset means it simply shows the scene's grid, exactly as before. Any of `gs`, `gc`, `gv` set gives it its own grid inside its edges, with the first line on its top left corner; the scene's grid is left out of that patch (`squareLines` with holes) and `gv` is its own on/off switch even when the scene's grid is off. **Only the square size, colour, switch and paper are per map: feet per square, the diagonal rule and square or hex stay the scene's.** `client.gridAt(point)` is the grid that counts at a spot (the scene's own object when no map has one) and `client.mapGrids` the list; token size, snapping (drag, nudge, teleport, add, duplicate), hit tests, the ruler, test-move distance and light and sight radii use it. Everything else (spell templates, heights and painted ground, walls snapping, fog) keeps using the scene's grid, so a map with squares of its own is for tokens and looks, not for those. An empty grid keeps its number of squares when its square size changes. Tests: `tests/mapgrids.test.ts`, `tests/client.test.ts`, `tests/e2e/batchZ18.mjs`.
- Spell templates always highlight covered cells on gridded maps. Gridless maps show a continuous footprint. Both clip at playable map edges.
- The spell tool opens in Place on an empty map. Select lets a user move, resize, delete, or adjust an individual template. Advanced settings in Place supply defaults for new spells. Each placed spell saves its own settings.
- Double-click a spell to select it. A visible token takes priority over a spell and its resize handles when picking. Line spells travel straight across their full width. Walls can block part of that width, and openings pass the corresponding strip through.
- Gridded spell ranges snap to 5 ft in three dimensions. Save the range with the spell and project it along its bearing when elevations change. Selection and resize handles use the rendered footprint. Board measurements display whole feet while geometry retains its precision.
- Spell elevation fields are absolute feet and default to the ground under each endpoint. The far endpoint lies on the axis of aimed spells. Use `spellVolume` for creature intersections, range, and wall crossings. Wall wrapping spends range and applies only to area spells. A token shows one colored arc per visible spell that reaches its body.
- Spell highlights and token hits respect solid terrain along the cast when elevation is enabled. A line starts at a vertical cut through its origin. Put resize handles on the projected forward rim. Show face edges on tilted cubes and the circular end on tilted cones. Advance the placement palette after each cast and keep a custom color until the user chooses a swatch.
- Spell shells use an overhead view so every point shares its map coordinates with targeting. The bright border and stronger tint mark reachable ground at its actual height. Erased terrain-wall openings let spells pass underneath raised decks. Compute wall-aware coverage and shaded faces off the drawing thread, coalesce drag requests, and use full detail after placement. Token hits use the original world-space volume.
- **Player view is a switch in the Players tab and a toolbar button.** The Players tab opens with a plain "Player view" switch (a `Toggle`, never a menu) and the eye button between the grid and fog buttons (key **O**) does the same; they, the Scene panel and fog switches and the note's Stop all set `ui.dmPreview`, so they always agree. The eye's label changes to "Back to the DM view" while it is on. No per-player "see as": every token with sight shares one vision, so it would look the same as the general preview.
- **A scene can be just a grid.** A page with no picture is `mapUrl: null` with `mapW`/`mapH` above zero (`isBlankPage`); an empty grid beside a map is an extra map whose `url` is `blank:` (`isBlankMap`, `core/blankgrid.ts`). Both are drawn as tinted white sprites (`paperColour` of the grid colour, so the lines show) on a dark scene background (`BLANK_BG`); `sceneRect` counts them; extra blanks are placed on grid lines (`blankSpot`) and sized in squares. Everything that asks for "a map" must also accept a blank page (`isBlankPage`), e.g. the "no map yet" chip.
- **One window adds a map: upload, library or an empty grid.** `AddMapModal` (in `modals.tsx`) is the only way to add an extra map. A library pick adds at once, an upload says what it is doing and can be saved to the library. `MapLibraryGrid` and `usePageDrop` are shared with New scene.
- **The DM opens a player's card from the Tokens tab.** `PlayerCardModal` (`ui/playerCard.tsx`) lists that player's saved tokens (`tables/$tid/chars/$rid`, which the DM may write) with the token editor in its `saved` mode (no placement-only fields; hit points are the DM's Maximum) and the handouts addressed to them or to everyone, opened in the ordinary handout editor. Handouts are DM-made only; players do not write any.
- **A reload keeps the scene you were looking at.** The DM's view scene is remembered per table in that browser (`vtt-view-scene:<tableId>`); the live scene still decides what players see. Only a scene the DM opens on purpose is remembered (`openScene(sid, auto)`; the guess made on arrival is `auto` and is replaced if the remembered scene turns up later), and a remembered scene that no longer exists falls back to the live one.
- **The initiative window shows only what applies.** The round counter and the previous and Next turn buttons appear only when there is an order; there is one place to roll (Roll all empty) and one button that adds the rolled tokens. No instruction lines or "nothing here" lines for empty states.
- **Dropdowns in the top bar are centred.** The generic `select` rule pins a dropdown to the start of its row (so it never stretches in a column); `.pill select` overrides that with `align-self: center`. A new control in the bar must be checked at 1366 by 768 for being in the middle.
- **Short notes.** A standing note on screen is two or three words ("Hidden from players") and the longer reason is its tooltip. File buttons say "Upload a picture…".
